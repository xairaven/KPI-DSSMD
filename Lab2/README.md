# Лаб. 2 — Абітурієнт (MVC)

Android-додаток на Tauri (Rust + React/TypeScript). Домен: абітурієнт
(ID, Прізвище, Ім'я, По-батькові, Адреса, Телефон, Оцінки).

Завдання вимагає MVC з окремою Activity та моделлю на кожен пункт (a-в).
Tauri-застосунок технічно складається з однієї Activity (вона монтує
системний WebView), тож "окрема Activity" відтворена функціонально:
кожен пункт — окремий маршрут (екран) з власним стеком навігації
(`react-router-dom`, `HashRouter`), власною Rust-командою-контролером і
власною моделлю-представленням даних.

## Структура

- `src-tauri/src/applicant.rs` — Model: сутність `Applicant` і чисті
  функції бізнес-логіки (середній бал, незадовільні оцінки, поріг,
  напівпрохідний бал). Нічого не знає про Tauri чи UI.
- `src-tauri/src/repository.rs` — Model: спільне мутабельне сховище
  (`Mutex`, керований стан Tauri). На відміну від Лаб.1, дані повинні
  зберігати стан між екранами, бо тут є редагування.
- `src-tauri/src/sample.rs` — початковий масив із 10 абітурієнтів.
- `src-tauri/src/screen/` — Controller: по одному модулю на кожен пункт
  завдання плюс екран введення/редагування:
  - `failing.rs` → (a) незадовільні оцінки
  - `threshold.rs` → (б) поріг середнього балу
  - `top.rs` → (в) топ-N та напівпрохідний бал
  - `students.rs` → список, додавання, редагування
- `src/screens/` — View: `Home.tsx` (меню), та по одному екрану на
  кожен Controller вище. Жодної бізнес-логіки, лише відображення та
  виклик `invoke()`.
- `src/components/ApplicantTable.tsx` — спільна таблиця, яку
  перевикористовують екрани звітів.

## Запуск

```sh
pnpm install
pnpm tauri android dev   # Android-емулятор
pnpm tauri dev            # десктоп, для швидкої перевірки
```
